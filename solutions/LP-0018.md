## Summary

`logos-osm` distributes Geofabrik OpenStreetMap PBF snapshots through Logos. It consists of:

- an on-chain **OSM registry LEZ program** (RISC Zero guest, ported to the LEZ v0.3.1 plan/apply API) that stores per-region entries (`region`, `parent`, `level`, `cid`, `source_url`, `checksum`, `version`, `hosted`, `timestamp`) in a public registry PDA, with single and batch registration;
- a Rust **SDK** (`osm_sdk`) covering discovery of the frozen 72-region predefined set, Geofabrik MD5 verification, hosting, local import, registry queries by region / parent / CID, download (Storage by CID, Geofabrik fallback) and update checks;
- an `osm` **CLI**, a C **FFI**, a Basecamp **core module** (`osm-module`), a QML **distribution app** (`osm-app`) and a separate **consumer example module** (`examples/basecamp-consumer`), built with `logos-module-builder`.

The program has been deployed to the **public Logos testnet v0.3** as a practice deployment and smoke-tested (init + register + read-back). On that deployment, **28 real Geofabrik regions across 20 countries** are now hosted in Logos Storage and registered on chain (25 from the coverage run, plus greece, chile and belarus from the bulk host and local import runs), with keyless verifies passing 25/25 and 3/3 on the hosting node (see [Coverage on testnet v0.3](#coverage-on-testnet-v03)). Retrieval of that data by an independent node over the network is **not yet proven**. The **testnet 0.4** deployment required by the prize is pending because testnet 0.4 is not yet live.

## Approach

**Registry program.** One public registry PDA (seed `registry`) owned by the program holds a Borsh-encoded `Registry` keyed by the Geofabrik region path, so `region` is unique and `parent` / `level` place it in the tree. Instructions: `init_registry`, `register_region`, `register_batch` (multiple regions in one transaction for bulk hosting). Validation (non-empty region, valid level, checksum format, timestamp) lives in a shared crate, `osm_registry_core`, used by both the guest and the SDK so client-side and on-chain checks cannot drift. Queries by region, parent and CID are done off-chain by reading the registry account and decoding it, which keeps the on-chain program small; results are ordered by timestamp (region path as tie-breaker). A size bound test keeps the registry under the LEZ 100 KiB account ceiling for the closed region set.

**SPEL vs. LEZ v0.3.1.** The program was first written against SPEL / the older `ProgramInput` API. Public testnet v0.3 runs LEZ v0.3.1, which replaced that API with the plan/apply model (`run_program(plan, apply)`, shard effects, segmented program upload), while upstream SPEL still targets LEZ v0.2.5-rc2. To run on a real public network we ported the guest to v0.3.1 directly rather than wait for SPEL. As a consequence the IDL is currently produced by an in-repo generator (`make idl`, checked for freshness in CI) that describes the plan/apply instruction and account contract, not by SPEL tooling; see the IDL criterion below.

**Region model.** The predefined, non-overlapping set (48 country-level entries and 24 subregions of US, India, China and Russia) is frozen in `regions.json` and embedded in the SDK, so discovery works without network access; `--refresh` pulls fresh canonical URLs from the Geofabrik index. Because the set is a partition, bulk host never creates parent/child overlap.

**Integrity.** Geofabrik's published MD5 is checked at fetch/import time only; after that, integrity comes from the Storage CID recorded on-chain, so downloads of hosted regions do not need Geofabrik.

**What did not work / known gap.** The first Storage adapter (`LogoscoreStorage`) targeted the legacy Storage module API (`uploadFile` / `downloadFile` / `nameObject`). It has been replaced by `LogosctlStorage`, which calls the current `storage_module` 3.0.2 API (`uploadUrl` / `downloadToUrl`) through logosctl 0.3.2 and waits for the completion events. A real upload-download of the 3,507,206-byte Andorra PBF passed on one local Storage node with matching MD5 and SHA-256, and the 25-region coverage run (below) then did fetch → MD5 → store → fetch-back → register → registry read-back → download-by-on-chain-CID against real Storage and the public testnet v0.3 for every region, on that one node. Not yet done: a multi-node transfer (independent nodes and GitHub Actions runners discovered the hosting node but could not complete a transfer, because the hosting box is behind NAT and the testnet relays dropped the streams) and a green real-Storage retrieval leg in CI (the CI end-to-end tests still use an in-memory Storage double).

**Fee bug found during coverage hosting.** Registrations started failing with the sequencer's generic "Incorrect fee" error. The cause was the fee-reserve screen (`PayerCannotFund`): the wallet declares `gas_limit = 2,000,000` by default, so the reserve exceeded the payer's balance although a `Register` actually costs about 1.1–1.2M. The client now sets `--gas-limit` (500,000 for the coverage run), preflights the payer balance against the reserve with an explicit error, and reconciles slow confirmations via `getTransaction` instead of resubmitting. The on-chain program is unchanged.

**Why Logos.** Map distribution today depends on central hosts. A registry on LEZ gives a censorship-resistant, publicly auditable index of which snapshot (by CID and checksum) is authentic for each region, with no operator able to silently swap data; Logos Storage lets many independent operators mirror the same CID, and content addressing means a downloader never has to trust the mirror. A centralised alternative would reintroduce a single party who can withhold or alter the index.

## FURPS Self-Assessment

Full assessment: [`docs/furps.md`](https://github.com/YodHeVauHe/logos-osm/blob/main/docs/furps.md).

### Functionality

Registry program with `init_registry`, `register_region`, `register_batch`; SDK/CLI for discovery, host, bulk host, import, lookup (region / parent / CID), update check and download. 28 regions / 20 countries hosted and registered on testnet v0.3. That includes one bulk-host batch transaction and one local import, and the registry-backed verifies pass 25/25 and 3/3 on the hosting node. Limitation: multi-node Storage transfer (retrieval by an independent node) is not yet verified. Out of scope by design: live OSM sync, rendering, routing, custom regions.

### Usability

`osm discover` works with no chain or Storage configuration. Registry commands need a program ID, wallet home and fee payer (`OSM_RPC_URL`, `LEE_WALLET_HOME_DIR`). SDK guide with a resolve-to-CID worked example and a consumer module example. The Basecamp app builds in CI and both modules are published in the module catalog (linux-amd64). On Linux the catalog 1.0.2 app loads in Basecamp, shows the testnet v0.3 registry's hosted regions, and downloads a hosted region with a verified checksum (logos-osm PR #12). Hosting from the app and macOS are not yet verified.

### Reliability

Shared validation between guest and SDK; MD5 mismatch fails before registration; exponential back-off retries on network/Storage operations; timestamp-ordered query results; registry size bound tested against the 100 KiB account limit. Registration is idempotent per region path (upsert).

### Performance

Localnet guest cycles: 3,801 for a one-entry register and 4,877 for a two-entry batch (LEZ v0.3.1, RISC Zero dev mode). Queries are off-chain reads of a single account.

### Supportability

Workspace split into shared types, guest, SDK, CLI, FFI, Basecamp module, app and consumer example. CI on `main`: fmt, clippy and tests (Ubuntu, Windows), in-memory e2e, Nix builds of module and app, and a job that builds LEZ v0.3.1, deploys the guest to a standalone sequencer, checks IDL freshness and runs on-chain register/query e2e. Deployment steps and program IDs are in the README.

**Reproducibility.** Versions (LEZ v0.3.1, `logosctl` 0.3.2 with SHA-256, `storage_module` 3.0.2, network `logos.test`), the RPC, program ID, registry PDA and the 25 regions are pinned in [`coverage/regions-testnet-v0.3.json`](https://github.com/YodHeVauHe/logos-osm/blob/main/coverage/regions-testnet-v0.3.json). From a clean checkout:

```sh
tools/coverage.sh setup   # fetch + sha256-check logosctl 0.3.2, build osm and osm_registry_cli
tools/coverage.sh node    # start a Storage node on logos.test
tools/coverage.sh host    # needs a funded LEZ wallet; idempotent, skips regions already hosted on chain
tools/coverage.sh verify  # keyless: no wallet or key
```

`verify` reads the registry with the sequencer's `getAccount` JSON-RPC, decodes it, downloads each on-chain CID through a Storage node and compares the bytes with the on-chain checksum (`--registry-only` checks the chain side alone). The same steps are available as `make coverage-*` targets. A `storage-retrieval` GitHub workflow runs the keyless verify from a fresh runner as the public network check.

**Not proven: network retrieval.** All 28 objects sit on one Storage node on a box behind NAT (private address, Cloudflare egress, port mapping failed, relay-only addresses). Two fresh verifier nodes and three GitHub Actions runs ([41330147318](https://github.com/YodHeVauHe/logos-osm/actions/runs/41330147318), [41331443910](https://github.com/YodHeVauHe/logos-osm/actions/runs/41331443910), [41331566883](https://github.com/YodHeVauHe/logos-osm/actions/runs/41331566883)) found the hosting node as a provider but did not complete a transfer. The latest `storage-retrieval` run, on the final PR #7 head ([41335257985](https://github.com/YodHeVauHe/logos-osm/actions/runs/41335257985)), fetched the public Logos docs control CID (2,276,462 bytes in 7.1 s) but 0/2 of our regions (`china/henan`, `kenya`: no download completed within 600 s; the `kenya` manifest was not found). That workflow's verify step is `continue-on-error`, so its green status does not mean a retrieval succeeded. The fix is a publicly reachable Storage node seeded with the same bytes; the steps are in the coverage doc. These CIDs should not be treated as online until an independent fetch succeeds.
