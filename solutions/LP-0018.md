# Solution: LP-0018 — OpenStreetMap data distribution on Logos

**Submitted by:** aegonmyy

## Summary

An OpenStreetMap distribution system for the Logos ecosystem: a Basecamp app
that discovers Geofabrik regions, hosts their map data in Logos Storage, and
registers each hosted snapshot on-chain in an OSM registry LEZ program; a
separate SDK/module that other Basecamp apps and modules depend on to resolve
a region to its CID and metadata; and a CLI covering the same operations.

Integrity does not rest on trusting a mirror. Every hop recomputes a streaming
MD5 of the bytes and checks it against Geofabrik's published checksum for that
snapshot, and the registry records that checksum next to the storage CID. A
consumer that fetches a region from Logos Storage verifies the same checksum a
Geofabrik user would, so the map data is verifiable without a round trip to
Geofabrik, and a host cannot silently substitute bytes.

## Approach

### Architecture

Three layers, each usable without the one above it:

**The LEZ program** (`osm_registry`) holds the registry. There is one registry
account, holding initialization state and the set of covered region paths, and
one region account per region of the predefined set, holding that region's
mirror list. Each mirror records the registering account, the storage CID, the
Geofabrik checksum, the snapshot version, and the timestamp. Registration is
permissionless: any signer may mirror a region, which is what lets the adoption
criteria be read directly off the chain.

**The SDK** (`osm-sdk`) is a Rust crate with a C ABI (`liblogos_osm`), so both
the Logos Core module and the CLI drive the same lifecycle code. It exposes
region discovery, hosting, registration, query by region and parent, mirror
lookup by CID, fetch, local import, and update checks.

**The Basecamp app** is a QML module that talks to the core module over
RemoteObjects. It shows hosted status, snapshot versions, and verification
results, and covers both the host/registrar flow and the consumer flow.

### Decisions, with the alternatives

**A closed, non-overlapping region set embedded in the program.** Geofabrik's
index is a tree, and a parent extract is the byte-for-byte union of its
children. Registering both a country and its subregions would double-count
geography and let the same bytes be advertised twice. The program therefore
embeds a frozen set of 72 regions (48 countries and 24 subregions, with the
four largest countries decomposed into subregions only) and rejects any path
outside it, so the partition is enforced by the chain rather than by client
good behaviour. `parent` and `level` come from the embedded table, never from
the registrant's claim.

**Integrity anchored to Geofabrik's published MD5, not to a signature.** The
alternative was to have registrars sign their uploads. That proves who uploaded
bytes, and says nothing about whether the bytes are the real OSM snapshot for
that region on that date. Pinning to Geofabrik's published checksum means an
evaluator can independently confirm any hosted region against the canonical
source, and it is the property the prize's coverage criterion is written
against.

**Permissionless registration, with the owner recorded only for provenance.**
The alternative was an owner-gated registry. That would make the coverage
criterion depend on one account, and the prize wants multiple independent
registrars per region, so the ownership check would work against it. The owner
is recorded at `Init` for provenance and future admin instructions.

**A separate SDK module rather than only an app.** The prize calls out that a
consumer needs the PBF files and a way to resolve them, not the distribution
UI. Publishing the SDK as its own module means a consumer app depends on a
small surface and does not pull in the distribution app.

### Why the Logos stack

The deliverable is a distribution layer for large public binary assets where
the interesting property is verifiable availability. Logos Storage gives
content addressing, so a fetched file's identity is its hash and a storage node
cannot hand back different bytes without the check failing. LEZ gives the
registry a public, timestamped ledger that no participant controls, which is
what makes "which regions are covered, by whom, since when" checkable by a
third party from chain data alone. Geofabrik's index and checksums remain the
canonical source of the data itself.

Built on a centralised alternative, coverage would be a database row asserted
by whoever runs the service, and the adoption evidence would be worth exactly
as much as trust in that operator.

- [x] **Region discovery**: fetches the Geofabrik index, cross-checks it against
  the frozen set, and reports each region's level in the tree.
- [x] **Host workflow**: download from Geofabrik, verify the published MD5 while
  streaming, store to Logos Storage, register on-chain.
- [x] **Download workflow**: fetch from Logos Storage, with Geofabrik as the
  direct fallback when a region is not hosted. Integrity is checked against the
  registry's recorded checksum in both paths.

  skipped region is reported rather than treated as an error, and one region's
  failure does not abort the run.

  currently published MD5, then stored and registered by CID.

  independently.
- [x] **On-chain registry**: stores region, parent, level, cid, checksum,

## FURPS Self-Assessment

### Functionality

The CLI has eleven subcommands covering the full lifecycle. The registry
handles single and batch registration with a cap of 24 regions per transaction,
and retains at most 32 mirrors per region (oldest pruned) so the version trail
stays bounded while the recent history is preserved. Reads cover by-region, by-parent,
and by-CID.

### Usability

The Basecamp app's host flow walks from region selection through hosting to the
registration transaction, showing hosted state, snapshot version, and
verification result. The consumer flow resolves a region to its CID and fetches
it. The same operations are available from the CLI, so the system is scriptable
and testable without a GUI.

### Reliability

The integrity spine is the streaming MD5 check, applied on download from
Geofabrik, on local import, on storage round trip, and on fetch from Logos
Storage. Storage uploads retry with exponential back-off. The registry rejects
out-of-set paths, malformed versions, wrong region accounts, and unsigned
registrations, each with a specific message.

### Performance

See the cycle table above. Measured against the standalone sequencer in release
mode; the numbers are the guest's user cycles and the total cycles the sequencer
bills, for the account counts shown. Hosting throughput is dominated by the
Geofabrik download; a 339 MB region (Greece) completed in 220 s wall with 32 MB
peak RSS.

### Supportability

The workspace separates the shared instruction and state types (`osm-core`), the
SDK, the CLI, the guest program, and the host-side deployment crate, so the
on-chain logic runs as ordinary host unit tests. The guest artifact is committed
with its program id pinned in `build.rs`, and a test asserts the bytes, the id,
and the documentation agree.
