# Solution: LP-0013 — Token Program: Mint Authority (RFP-001)

**Submitted by:** LeonardoRyuta

## Summary

A complete, production-oriented mint authority stack for the LEZ/NSSA ecosystem.
Implements all four RFP-001 hard requirements: authority-gated minting, authority
transfer, irreversible revocation, and a runtime-agnostic client library — delivered
as two on-chain Risc0 zkVM programs (`mint-program`, `ata-program`), a zero-dependency
Rust library (`mint-core`), and a unified CLI (`wallet-ata`).

Submitted jointly with LP-0014 (Associated Token Accounts) because the two tracks
are architecturally unified: LP-0013 defines *who can issue tokens*; LP-0014 defines
*where those tokens are stored*.  Both share the same deterministic address derivation
formula and Borsh account layout, so wallets and indexers need only one formula to
find any balance regardless of which program created it.

## Approach

### Two-layer architecture

`mint-core` (library) is fully decoupled from `nssa_core` and the Risc0 toolchain.
Wallets, indexers, and bridges embed it for pre-flight authority validation and
instruction JSON building without pulling in the ZKP execution environment.

`mint-program` is the Risc0 zkVM guest binary that enforces all state transitions
on-chain.  The clean split means the library can be published independently and
consumed by any Rust project, satisfying RFP-001's requirement for a
"self-sufficient, agnostic library."

### Shared ATA address space with LP-0014

Token holding accounts created by `MintTo` live at the same deterministic address as
ATAs defined by LP-0014:


address = AccountId( Keccak256( "NSSA_ATA_V1" || owner_bytes || mint_bytes ) )


The `TokenHolding` Borsh layout is byte-for-byte identical to `AtaData`.  One formula,
one layout — block explorers and indexers read balances uniformly from both program types.

### Irreversible revocation as a first-class on-chain invariant

`SetMintAuthority { new_authority: null }` sets `has_authority = false` on the
`MintDefinition` account.  No instruction can re-enable this flag.  The credible
commitment to a fixed maximum supply is enforced entirely in the program, not by
client-side convention.

### Configurable program ID

Every `wallet-ata` mint command accepts `--mint-program <ID>` (or reads
`$MINT_PROGRAM_ID`) so the same CLI binary works against any deployment without
recompilation.

## Success Criteria Checklist

- [x] **Mint authority initialised at program launch** — `CreateMint { authority: Some(A) }` stores the authority key and sets `has_authority = true` in the on-chain `MintDefinition` account.
- [x] **Authority can transfer to a new signer** — `SetMintAuthority { new_authority: Some(B) }`, signed by the current authority, atomically replaces the stored authority key.
- [x] **Authority can revoke/renounce completely and irreversibly** — `SetMintAuthority { new_authority: null }` sets `has_authority = false`; no inverse operation exists in the program.
- [x] **Authority exclusively gates the privileged minting function** — `MintTo` enforces five sequential guards (signer check, mint-ID integrity, initialisation, revocation state, authority-key match) and rejects any transaction that fails any of them.
- [x] **Runtime-agnostic library** — `mint-core` has zero dependency on `nssa_core`; compiles on stable Rust for any target.
- [x] **End-to-end sequencer integration** — `docs/examples/lp0013_sequencer_integration.sh` exercises the full lifecycle (create → mint → transfer authority → mint → revoke → rejected mint) against a live LEZ sequencer and prints a `PASSED` banner.

## FURPS Self-Assessment

### Functionality

Supported operations:

| Instruction | CLI command | Effect |
|---|---|---|
| `CreateMint` | `wallet-ata create-mint` | Initialises mint definition; sets authority and decimals |
| `MintTo` | `wallet-ata mint-to` | Issues tokens to destination; creates holding account if absent |
| `SetMintAuthority` | `wallet-ata set-mint-authority` | Transfers authority (with `--new-authority`) or revokes it permanently (without) |
| `TransferViaMint` | `wallet-ata transfer-via-mint` | Peer-to-peer transfer within `mint-program`'s ownership domain |
| `get-mint` | `wallet-ata get-mint` | Reads and displays mint definition state |
| `list-atas` | `wallet-ata list-atas` | Lists all token balances for a wallet across one or more mints |

Limitations: `TransferViaMint` only moves tokens between accounts claimed by
`mint-program`; tokens in `ata-program`-owned accounts use `transfer` instead.

### Usability

- Single binary (`wallet-ata`) covers all LP-0013 and LP-0014 operations.
- `--help` on every subcommand; all flags have descriptive names.
- `--mint-program` flag (or `$MINT_PROGRAM_ID` env var) avoids re-specifying the deployed program ID on every call.
- Six runnable shell-script examples in `docs/examples/` demonstrate every workflow end-to-end with no manual steps beyond starting the sequencer.
- `derive-ata` is a pure offline command (no RPC call) for quick address lookups.

### Reliability

- `set -euo pipefail` in all example scripts; any unexpected failure aborts immediately.
- All on-chain arithmetic uses `checked_add` — supply and balance overflows abort the transaction rather than wrapping.
- All derived addresses are verified on-chain before use; a manipulated account list cannot redirect funds.
- `CreateMint` is guarded against re-initialisation; `MintTo` verifies the mint account ID matches the instruction argument, preventing fake-mint substitution.
- Authority revocation is irreversible by construction — no administrative escape hatch.

### Performance

- `mint-core` instruction builders are pure in-memory operations (no I/O, no allocation beyond JSON serialisation).
- On-chain handlers are intentionally minimal: `MintTo` reads two accounts, writes two, performs one Keccak-256 derivation.
- No loops or unbounded iteration in any handler; per-transaction compute cost is O(1).
- `derive-ata` (offline) returns in < 1 ms on any modern host.

### Supportability

- **49 unit tests** across `ata-core` (17), `mint-core` (11), `mint-program` (21); all pass on stable Rust ≥ 1.85 via `cargo test`.
- Workspace default members (`ata-core`, `mint-core`, `ata-cli`) build and test without the Risc0 toolchain, lowering the CI barrier.
- On-chain crates (`ata-program`, `mint-program`) are isolated workspace members; they require the Risc0 target only for the final binary build.
- `MINT_AUTHORITY.md` documents the Borsh account layouts, all instruction semantics, guard ordering, security properties, and RFP-001 compliance in a single reference document intended for future maintainers.
- Program ID is injected at runtime — no source changes needed to redeploy.

### Reproducing the E2E demo

```sh
# 1. Start the LEZ sequencer
cd logos-execution-zone
RUST_LOG=info cargo run --features standalone -p sequencer_runner \
    sequencer_runner/configs/debug

# 2. Build and deploy mint-program (requires Risc0 toolchain)
cargo build --release --target riscv32im-risc0-zkvm-elf -p mint-program
wallet --rpc http://127.0.0.1:3040 \
    deploy-program target/riscv32im-risc0-zkvm-elf/release/mint-program

# 3. Run the full LP-0013 integration demo
bash docs/examples/lp0013_sequencer_integration.sh
```
