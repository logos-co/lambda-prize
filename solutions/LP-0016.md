# Solution: LP-0016 — Anonymous Forum with Threshold Moderation and Membership Revocation

**Submitted by:** Kilian Valdman ([@forever8896](https://github.com/forever8896))

## Summary

A forum-agnostic threshold-moderation library plus a working Logos Basecamp app demonstrating the full lifecycle: members register with a stake and post unlinkably; an N-of-M moderator quorum jointly issues strikes off-chain via threshold ElGamal; after K strikes against the same author, anyone can submit a single on-chain slash transaction that the membership-registry SPEL program verifies (Merkle inclusion + Lagrange reconstruction + N moderator ECDSA signatures per certificate) and that revokes the member, claims the stake, and prevents future posts under that commitment.

All forum activity (posts, certificate shares) flows over Logos Delivery on per-instance content topics. The on-chain piece is the membership-registry SPEL program; nothing else hits the chain except registration and the slash itself.

## Approach

### Crypto core

A member's identity is a Shamir polynomial of degree K-1 over the secp256k1 scalar field: `f(x) = sk + a₁x + … + a_{K-1}x^{K-1}`. The on-chain commitment is `C = SHA-256(domain("commitment") || sk || a₁ || … || a_{K-1})`. SHA-256 was chosen over Poseidon because the LEZ RISC0 guest accelerates SHA-256 via a precompile but does not accelerate Poseidon — and because we run inside a RISC0 guest rather than a SNARK, the "Poseidon is small in arithmetic circuits" advantage is irrelevant.

Each post embeds an **encrypted Shamir share** `(xᵢ, yᵢ = f(xᵢ))` under the forum's threshold ElGamal public key. The author chooses a fresh random `xᵢ` per post — never reused — so unlinkability is information-theoretic for any < K shares (Shamir's perfect secrecy). When N moderators jointly decrypt and K decrypted shares accumulate, Lagrange interpolation recovers `f`, hashes back to `C`, and the slash succeeds.

### On-chain registry (SPEL program)

`forum_registry` is a SPEL/LEZ program with four instructions: `create_instance`, `register`, `submit_slash`, `reveal`. The slash handler runs entirely on-chain:

1. Verifies the recovered commitment is in the membership Merkle tree (sorted-pair SHA-256, depth D).
2. Verifies the commitment is NOT in the on-chain revocation list.
3. Lagrange-interpolates the K (xᵢ, yᵢ) points in the secp256k1 scalar field, recovers the polynomial coefficients, hashes them, and confirms the result equals the claimed commitment.
4. **Verifies all N×K ECDSA-secp256k1 signatures** of the moderator certificate shares against the on-chain roster (closes the "colluding mod quorum" gap that would otherwise let ≥N moderators secretly slash without leaving an off-chain audit trail).
5. Adds the commitment to the revocation list, transfers the staked amount to the slash recipient.

### Off-chain transport

Two content topics per instance:

- `/logos-forum/1/<program_id_prefix>/posts/v1` — post envelopes (proof + ciphertext + opaque payload).
- `/logos-forum/1/<program_id_prefix>/certs/v1` — moderator certificate shares.

The Backend uses `LogosAPIClient::invokeRemoteMethodAsync` with `delivery_module` for `createNode` / `start` / `subscribe` / `send`, and `onEvent` to receive `messageReceived`. Build-time gated behind `FORUM_HAS_LOGOS_API` (set by the Nix flake at `.lgx` build time); standalone Qt preview builds without the SDK.

### Why the Logos stack

- **LEZ + RISC0 guest execution** — the slash handler runs the same RISC-V VM whether the client is producing a private TX proof or the sequencer is executing a public TX. The Lagrange + ECDSA + Merkle check fits comfortably in the guest's compute budget.
- **SPEL framework** — auto-generates the IDL from `#[lez_program]` macro annotations, so the wire format and the on-chain dispatch stay in sync. Prize criterion explicitly required SPEL.
- **Logos Delivery** — pub/sub over content topics matches the forum's broadcast pattern (every member needs every post and every cert) without an ordering requirement (we don't need consensus on post order). Censorship-resistant transport pairs naturally with on-chain enforcement: a censored cert just delays a particular strike; the slash mechanic still works once N out-of-band moderators bring their shares back online.
- **Why not a centralised alternative:** the entire point of this protocol is that *no party*, including moderators in fewer-than-N quantity, can deanonymize a member. A centralised host would have to be trusted with the post stream; the public-by-default off-chain certificate trail wouldn't be auditable; and the slash/revocation enforcement would have no trustless anchor.

### Trade-offs we considered and rejected

- **Poseidon over SHA-256:** rejected because LEZ's RISC0 guest accelerates SHA-256, not Poseidon, and we don't run inside a SNARK.
- **BLS12-381 for the threshold scheme:** considered for cleaner threshold pairings, rejected because k256 (secp256k1) is RISC0-accelerated and we already need it for ECDSA cert signatures. Adding a second curve would inflate guest binary size and proving time.
- **Distributed Key Generation (DKG):** deferred. v0.1 has the forum creator generate the threshold ElGamal keypair via Shamir SSS and distribute shares out-of-band. The trust assumption is bounded to instance creation; after that the creator has no special role.
- **Sparse Merkle revocation list:** deferred. v0.1 stores a flat `Vec<Hash32>`; the slash handler scans linearly. Acceptable up to a few thousand revocations; SMT would give constant-size non-revocation proofs at higher scale.
- **Shamir over GF(2⁸) (byte field) instead of the secp256k1 scalar field:** rejected because byte-level Shamir is brittle against any algebraic attack and incompatible with our threshold ElGamal scheme that already operates over secp256k1.

### Things that didn't work the first time

- **Sequencer in-Docker initially crashed silently** with "Main loop exited unexpectedly" right after the first `Validated transaction`. Root cause: the upstream `lez/sequencer/service/Dockerfile` installs `r0vm` (RISC-V VM execution server) as a sibling binary and sets `RISC0_SERVER_PATH=/usr/local/bin/r0vm` — without it, every transaction's mandatory clock TX silently fails. Fixed in `deploy/railway/Dockerfile` (now installs r0vm via rzup in the builder stage and copies it into the runtime image).
- **`sequencer_service` ignores the `port` field in its config JSON** — port comes from the `--port` CLI arg (default 3040). Without `--port $PORT`, Railway's HTTPS proxy returned 502 because the service was bound to 3040 instead of Railway's `$PORT=8080`. Fix: `entrypoint.sh` passes `--port $PORT` to the binary.
- **Default `max_block_size = "1 MiB"`** is too small to hold a `ProgramDeployment` tx with our ~660 KB guest binary plus borsh wrapping plus the mandatory clock TX. The deploy tx was silently dropped at block-creation time. Bumped to 4 MiB.
- **`spel inspect` prints the program ID in two formats** (`ProgramId (hex)` = u32×8 in BE; `ImageID (hex bytes)` = LE byte serialization). The `-p <hex>` flag expects the LE byte form; passing the BE u32-rendered form silently misroutes the create_instance tx and yields "Unknown program". Documented in our internal notes and the deploy script.
- **The IDL fixes the PDA seed at compile time** — to deploy two instances with different RISC0 image IDs, we maintain two source files (`forum_registry.rs` with seed `instance_v1`, `forum_registry_b.rs` with seed `instance_v2`) and ship two IDLs.

## FURPS Self-Assessment

### Functionality

The protocol implements every required primitive: registration with stake, anonymous posting with ZK membership proofs, N-of-M moderator certificate construction (threshold ElGamal decryption + ECDSA signing), K-strike accumulation with K-subset slash search, on-chain slash verification (Merkle + Lagrange + revocation + N×K signatures), and post rejection after revocation. Forum content type is intentionally opaque to the library — the demo app uses text posts, but `forum_moderation` makes no assumption about payload shape. Configurable per instance: K (strikes), N (sigs to issue strike), M (total mods), D (Merkle depth), stake amount, moderator roster.

### Usability

The Basecamp plugin presents four tabs (Posts / Moderate / History / Admin). All chain operations are reachable from QML buttons; no CLI or manual transaction crafting is required by the end user. Identity is generated and persisted in the wallet's home directory. The Admin tab handles instance creation including moderator-key distribution (printed once for the admin to relay out-of-band). The History tab shows every action and queued retry — important for a moderation app where audit trail is the point.

### Reliability

- Partial certificates (< N shares) are rejected client-side before any on-chain interaction (`AggregateError::NotEnoughShares`).
- Transient Logos-stack failures (delivery_module unavailable, sequencer hiccup) are queued in `m_pendingActions` and retried on an 8 s timer for up to 5 attempts. Status surfaced in the History tab.
- The slash handler validates inputs strictly: K mismatch, share-array length mismatch, duplicate moderator within a cert, signature failure all yield distinct error codes (30-37) so failures are debuggable.
- Per-post abscissa is randomly chosen per post — there is no shared nullifier whose consumption would block retries.

### Performance

- Off-chain crypto (commitment, Merkle, Shamir, threshold ElGamal, certificate aggregation, slash search): all sub-millisecond per op for forum-typical parameters.
- Slash search: K-subset enumeration is `O(t^K)` where `t` is the certificate-pool size. For K=3 with 100 outstanding certs ≈ 161 K interpolations; for K=5 with 50 certs ≈ 2.1 M. Both finish in a few seconds on a modern CPU. Incremental search (re-run only on new cert arrival) keeps amortized cost low.
- ZK post proof: ~1.5 M RISC0 cycles. Real-mode CPU: ~15-30 s; GPU: <5 s.
- On-chain CU costs measured on the live sequencer: `register` ~1.2 M, `submit_slash` ~3.8 M.
