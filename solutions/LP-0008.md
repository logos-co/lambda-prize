# Solution: LP-0008 — Autonomous AI Module with Wallet, Storage, and Messaging

**Submitted by:** Darlington A ([@darrojen](https://github.com/darrojen))

## Summary

An autonomous AI agent packaged as a **dynamically loadable Logos Core module** (built with `logos-module-builder`): a **shielded LEZ wallet**, **Logos Storage**, a **Logos Messaging owner channel**, **A2A-compatible agent-to-agent coordination**, and a **strictly enforced owner spending policy** — no custodian, no exposed APIs, no intermediary server.

The module follows the official Rust cdylib authoring model (the same one `chat_module` uses): a `.lidl` contract (`rust-lib/agent_module.lidl`) is compiled by `logos-lidl-gen` into the module ABI scaffold, and all decisions are delegated to **`agent-core`**, a host-independent Rust crate, which executes effects against the real Logos modules via generated typed clients — `chat_module` (e2e-encrypted owner channel), `delivery_module` (Logos Messaging content topics for A2A), `storage_module` (files), and `lez_core` (shielded accounts, transfers, program calls/deployments). All value movement passes a single dispatcher: **validate → authorize → spending policy → owner approval if required → panic-isolated execution**. State (approvals, tasks, spends, config, identity) persists under the host-assigned instance directory and survives restarts.

**Status / honesty note:** the decision core, policy engine, A2A layer, task lifecycle, persistence/recovery, CLI, and test suite are complete and tested — **78 tests green, CI workflows in place**. The gated sequencer integration suite has **passed against a real standalone LEZ sequencer with `RISC0_DEV_MODE=0`** (real shielded transfers, real client-side Risc0 proofs, on-chain receipt evidence). What is **not** yet verified is called out explicitly below and in [PRIZE-CHECKLIST.md](https://github.com/darrojen/logos_ai-agent/blob/master/PRIZE-CHECKLIST.md) and [docs/limitations.md](https://github.com/darrojen/logos_ai-agent/blob/master/docs/limitations.md): a live module load inside a running logoscore daemon, the public-testnet session (three agent deployments + CU measurements), and the narrated demo video (to be recorded and added as a comment on this PR). Nothing in this repo mocks a Logos API.

## Approach

### Architecture

The agent is a first-class Logos Core module, loaded and managed by the Logos Core runtime alongside the wallet, storage, and messaging modules — none of which are modified. Its identity is an **ed25519 messaging key bound to its own shielded LEZ account (NPK/ISK)**: on-chain it is indistinguishable from any other account holder, and its messaging address is derived from that identity.

- **Owner channel:** a dedicated 1:1 `chat_module` conversation, e2e-encrypted. The owner reaches the agent from any Logos app instance holding the owner's keys. Plain text goes to the pluggable inference backend; JSON control messages (`approval_response`, `skill_call`, `who_are_you`) drive the control plane.
- **Spending policy:** per-transaction threshold (default 10 LEZ atomic units) plus rolling-period caps. At/below threshold → autonomous execution. Above → a signed approval request goes to the owner over the encrypted channel and the transaction **holds**. Requests that never reach the owner, or that time out, are expired **fail-closed** — never executed. Decisions are first-wins and idempotent; everything persists across restarts.
- **Skills:** capabilities are discrete units behind a `skills::Skill` trait with a documented interface, so third parties add skills without touching the core module. All 21 default skills (storage, messaging, blockchain, agent coordination, meta) are implemented through it.
- **A2A compatibility:** Agent Cards follow the [A2A schema](https://a2a-protocol.org/latest/specification/) — signed JSON declaring identity, skills, I/O schemas, and the LEZ price per task, published to a Logos Messaging discovery topic. Task interactions follow the A2A lifecycle (working → input-required → completed/failed) mapped onto Logos Messaging envelopes; LEZ payment is transferred on task acceptance. This is documented as an A2A transport binding (`docs/a2a.md`): Logos Messaging replaces A2A's HTTP transport, and LEZ fills A2A's deliberate payment gap.
- **Skill isolation:** every dispatch runs under `catch_unwind`; a panicking skill is reported as a failed result and cannot crash the module or affect concurrently running skills.

### Key design decisions (and the alternatives rejected)

- **cdylib module + host-independent core crate** — the official Rust authoring model used by `chat_module`, rather than a standalone daemon: the module must load inside Logos Core alongside the other modules without modifying them (criterion F1). Isolating decisions in `agent-core` keeps the whole policy/task/skill logic testable without a chain (78 hermetic tests).
- **Single value-movement dispatcher** (validate → authorize → policy → approval → execute) rather than per-skill ad-hoc checks: one auditable chokepoint means no skill can move value around the spending policy — verified by tests like `non_owner_cannot_invoke_anything` and `period_cap_blocks_after_accumulation_end_to_end`.
- **Fail-closed approvals with retries then expiry**, rather than queuing indefinitely or executing on timeout: an above-threshold transaction that cannot reach the owner must never execute (criterion R2). Covered by `unnotified_approval_is_expired_fail_closed` and `timed_out`.
- **A2A over Logos Messaging content topics** with application-level signatures on every envelope, rather than trusting only the transport-reported sender: a malicious local module could spoof the transport-level sender, so enforcement combines owner-address check + signature verification + first-wins decision idempotency (`docs/security-model.md` T2). Defense in depth, not a single trusted source.
- **`storage.share` delivers the content address over the e2e-encrypted chat channel** rather than a native storage ACL: `storage_module` v2.1.3 exposes upload/download/manifests but no access-control API. This works today and stays interoperable; when an ACL API lands upstream, only `Effects::storage_share` changes — the skill surface is unchanged.
- **Pluggable inference** via an `Inference` seam (deterministic null backend shipped): the AI model is explicitly out of scope per the prize; wiring a local or API model is deployer configuration.

### Why the Logos stack

The agent needs exactly the four things Logos provides natively and a centralised cloud provider cannot: a **shielded LEZ account** gives the agent a sovereign wallet it controls (no custodian, no API keys), **Logos Messaging** gives the owner/agent and agent/agent channels end-to-end encryption with no intermediary server, **Logos Storage** holds the agent's files durably without an identity-tying host, and **LEZ** lets it take autonomous on-chain action within owner-set limits. A cloud-hosted equivalent would reintroduce every intermediary this design removes: the provider controls data and identity, imposes rent, and sits between the agent and its owner.

### What was tried and did not work (documented, not hidden)

- **Sequencer-only build fails:** a sequencer built without `wallet-ffi` tries to spawn an external `r0vm` binary for genesis execution and fails. The sequencer must be built *together with* `wallet-ffi` in one cargo invocation so the in-process prover is available — handled by `scripts/start-local-stack.sh`.
- **Stock debug genesis accounts have no public keys**, so a wallet cannot spend from them; `start-local-stack.sh --genesis-funder` derives a deterministic TEST-ONLY funder account offline (SHA256/secp256k1 x-only derivation matching the wallet runtime) and runs a custom genesis.
- **No Nix-capable environment at authoring time** → the module shell compiles under `nix build` (CI job) but has not been live-loaded in a logoscore daemon in this workspace; `rust-lib/src/deps.rs` exists specifically to absorb generated-name mismatches against the pinned `logos-rust-sdk` rev.
- **Full per-transaction LEZ history requires the indexer service** (the wallet FFI exposes balances/sync only) — `wallet.history` reports a sync snapshot plus journal-derived agent activity and says so in its output.
- **Public LEZ documentation does not publish a CU schedule** for the current testnet, so `docs/compute-units.md` ships a measurement plan and will be filled with measured figures from the testnet runs in this PR rather than invented numbers.

## FURPS Self-Assessment

### Functionality

21 default skills across five families; A2A-compatible agent-to-agent coordination with signed Agent Cards and a full task FSM; spending policy (per-tx threshold + period caps, fail-closed approval expiry, first-wins idempotency); owner authorization on all value movement; pluggable inference (null backend shipped, model choice is deployer configuration). Known gaps, stated: `storage.share` delivers the content address over the e2e chat channel (no native ACL API upstream); `wallet.history` is sync snapshot + journal-derived activity (full per-tx history needs the LEZ indexer); token-gated group admission is future work; no general time-window replay filter (dedup of approvals/task ids is exact; not load-bearing for the threat model).

### Usability

Install → build (cargo / nix) → `agent-cli keygen` → `agent-cli config --owner … --threshold …` → one-command profile deploy → chat with the agent from any Logos app, or drive it with `agent-cli interact` JSON control messages. Full walkthroughs in `docs/deployment.md` and `docs/owner-guide.md`; the demo recording checklist is in `docs/demo.md`.

### Reliability

Every state mutation persists before effects complete; tasks and approvals resume on load; notification retries with fail-closed expiry; per-dispatch panic isolation; signed envelopes reject tampering and impersonation. The gated suite exercises restart/persistence/failure scenarios explicitly.

### Performance

Measured on a 4-core laptop, local standalone sequencer, `RISC0_DEV_MODE=0`: autonomous private→private spend with client-side Risc0 succinct proof = 3331 s proving; full gated suite = 5341 s; 78 hermetic tests run in minutes. CU costs per on-chain operation (transfer, program call, deployment) will be measured on testnet and added to `docs/compute-units.md` in this PR — the plan is already there; no figures are invented.

### Supportability

78 hermetic tests (59 unit + 19 runtime integration); `cargo clippy -D warnings` and `cargo fmt --check` clean; 3-job CI on `master`; `PRIZE-CHECKLIST.md` maps every prize criterion to implementation/tests/evidence with an honest status; `docs/limitations.md` lists every known gap; `rust-lib/src/deps.rs` isolates generated-name drift against pinned upstream revs (logos-module-builder 0.2.6, logos-rust-sdk, chat_module 0.2.2, delivery_module v0.2.0, storage_module 2.1.3, lez_core 0.4.1).
