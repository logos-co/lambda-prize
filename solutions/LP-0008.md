# Solution: LP-0008 — Pilot, a Sovereign Agent Module for Logos Core

**Submitted by:** Johnnie Modebe (johnniedom)

## Summary

Pilot is an autonomous agent packaged as a **universal C++ Logos Core module** (`pilot_plugin`). The
`logoscore` runtime loads it alongside the unmodified wallet (`lez_core`), storage (`storage_module`) and
messaging (`delivery_module`) modules, and every wallet, storage and messaging action the agent takes goes
through those modules' typed interfaces — 56 call sites, no FFI, no vendored copies, no upstream patches.

The agent owns a shielded LEZ account and a public LEZ account it funds itself from the faucet, an
end-to-end-encrypted owner channel, a per-transaction and per-period **spending threshold** implemented as
a crash-reconciled nine-state machine in SQLite, **23 skills** (the 21 default skills plus `agent.import_card`
and a plugin loader) behind a documented third-party skill interface, and an **A2A-compatible** coordination
layer (JSON-RPC 2.0 over Logos Messaging, ECIES-encrypted, signed Agent Cards with first-contact identity
pinning) in which the asker pays the doer in LEZ on task completion. Inference is pluggable (Anthropic,
OpenAI-compatible endpoints, DeepSeek, Groq, OpenRouter, or none); no model is bundled.

Where the platform does not yet provide something (real zk proofs on an 8 GB laptop, a program call
without a documented ABI), the agent returns an honest error and the repository says so in
`KNOWN_LIMITATIONS.md` rather than faking a success.

## Approach

**One module, three dependencies, nothing bypassed.** Pilot is a `logos-module-builder` universal module:
pure C++ in `pilot_impl.h`, Qt glue generated at build time. Dependencies are declared in `metadata.json`
and reached only through the generated typed clients (`modules().lez_core`, `.delivery_module`,
`.storage_module`). We rejected the two shortcuts other approaches take — `dlopen`-ing the wallet library
or shelling out to the wallet CLI — because the prize asks for an agent that runs *inside* Logos Core
alongside the modules, and because module boundaries are what let the runtime restart, sandbox and
version each piece. The cost was real: the module host drops replies after its first event emission
(upstream), the wallet's remote calls have to be budgeted for a public chain that seals a block a minute,
and a cold wallet replays the whole chain before it answers. Each of those is handled in the module
(deadline-based waits, deferred storage-node start, a pull path for inbound messages) and documented.

**Money decisions default to inaction.** The spending threshold is a state machine
(`CREATED → HELD → NOTIFIED → APPROVED → EXECUTING → COMPLETED | TX_FAILED | EXPIRED | REJECTED`, plus a
terminal `TX_UNKNOWN` for crash-stranded transfers) persisted in SQLite WAL. A request above either limit
is held and the owner is notified over the encrypted channel; if the notification cannot be delivered the
request stays `HELD` and is re-announced on restart — it is never executed. Below-limit spends, owner
approvals and agent-to-agent payouts all run through one executor, so there is exactly one place where
money leaves the agent. Every failed spend records *why* on its own row.

**Two spend rails, chosen by the recipient's form.** The agent's shielded account pays with
`transfer_private` (payee keys) or `transfer_private_owned` (owned id); both need a client-side RISC0 proof.
The agent's public account — the one the faucet credits — pays with `transfer_public`, which the client
signs and the sequencer proves. `wallet.send` to `public:<64-hex id>` selects that rail. This is what lets
the agent settle on the public testnet from any machine; the shielded rail remains the private path and
needs ~16 GB of RAM for the prover.

**Asker pays doer on completion.** A2A settlement pays the doer's *declared, authenticated* price only when
the doer reports `completed`; never on `accepted`/`working`, never on `failed`/`canceled`. Reply
signatures are checked against the signing key pinned when the doer's card was first seen, not a key the
reply supplies, so a hijacked reply cannot redirect a payout. We considered escrow (pay on acceptance,
refund on cancel) and rejected it for v1: it needs an on-chain program and the wallet module exposes no
program operations (see below).

**Owner channel.** The agent derives an ECIES key pair for its inbox, publishes it in its Agent Card, and
holds an encrypted conversation with the owner over Logos Messaging. Confidentiality is not authority:
anyone who has read the card can encrypt to the agent, so owner commands are signed, pinned to the
owner's key on first contact, and replay-protected by a nonce, and once an owner is bound unsigned text
is dropped before it reaches the model or any skill. Two front-ends speak that channel from a separate
program, built from one library (`pilot-owner/src/owner_client.*`) with the agent's own crypto compiled
in: `pilot-owner` from a terminal, and the Basecamp plugin **Pilot Remote** from the Logos desktop app
through the `pilot_owner` module, so what either sends is exactly what the agent verifies and their only
network dependency is a Waku relay's REST API (the `pilot` chat CLI and the Pilot Agent plugin still reach
an agent on the same machine by daemon RPC). Over the channel the agent executes the owner's commands
itself and answers in text — before 2026-09-05 it echoed the raw action object the local CLI was meant to
interpret.

**What did not work, and what we did about it.**
- *Program operations.* An audit of an earlier wallet-module pin found no program entry point, and for
  months the `program.*` skills answered "unsupported (verified)" on its strength. The current pin
  (LEZ v0.2.2) does expose them; on 2026-09-05 the skills were wired to `get_account_public`,
  `send_generic_public_transaction` and `send_program_deployment_transaction`, still behind the threshold
  and trust gates. What Pilot does not have is any program's instruction ABI: `program.call` sends the
  words the owner supplies, and a call with real words has not been exercised (`KNOWN_LIMITATIONS.md` §1).
- *Dev-mode proofs on the public testnet.* The testnet accepts a dev-mode shielded transfer into its
  mempool and never mines it (measured 2026-08-29). Real proofs are required for the shielded leg.
- *Real proofs on an 8 GB laptop.* The prover holds ~4.5 GB inside a 5 GB VM and runs swap-bound for
  hours; six attempts never finished there. The same code path on a 16 GB hosted runner funded the
  agent's private account with a real proof in under an hour (`real-proof.yml`, run 33880084026;
  the claimed account `F1MB…` reads 150 → 50 on the chain). The public rail was built so that
  everyday testnet spending does not depend on a 16 GB machine.
- *Inbound events from the delivery host.* The host emits on its FFI thread and Qt drops every event and
  reply after the first; inbound A2A and owner messages are therefore also pulled from the relay's REST
  store. Filed upstream with the other first-report bugs we hit.

**Why the Logos stack.** The agent holds funds and keys nobody else can freeze, is reachable by its owner
over a decentralised transport with no server in between, stores encrypted files on a content-addressed
network, and settles with other agents in a shielded currency. On a centralised stack each of those
becomes a trust relationship with a provider: an API key that can be revoked, a message bus that can read
the traffic, a bucket that can be subpoenaed, a payment rail that can reverse. The stack's properties
are the product here, not a deployment detail.

## FURPS Self-Assessment

### Functionality

23 skills across storage (upload/download/list/share, AES-256-GCM per file, share re-encrypts the file key
to the recipient), messaging (send/join/create_group over Logos Messaging), wallet (balance/send/history on
two rails), program operations (query / call / deploy through the wallet module's transaction methods),
agent coordination (card/discover/import_card/task/subscribe/cancel with signed cards and paid tasks) and
meta (skills/status/configure). Limitations: `program.call` needs the program's instruction words from
the caller (no ABI is known to Pilot) and private program calls are not wired; `wallet.history` lists
the agent's own spend ledger, not inbound transfers (the wallet module exposes no transaction list). (Group invites, once plaintext, are now sealed to
each member and carry the AES-256-GCM group key; the receive side — `messagingInbox` — records direct
and group messages, invites and file shares, which until 2026-09-04 were decrypted and dropped.)

### Usability

`pilot deploy` brings up a headless agent (daemon, identity, funding, inference, owner binding); `pilot
chat` gives the owner a terminal conversation on the same machine; `pilot-owner` and the Basecamp plugin
Pilot Remote talk to an agent anywhere over the owner channel, both from one library, the plugin through
the `pilot_owner` module; the Pilot Agent plugin runs an agent inside Basecamp. Third parties add skills
by dropping a plugin `.so` into an operator directory (off by default). Gaps: the deploy selectors need a
terminal, and Pilot Remote's module and wire are proven headlessly while its window has not been clicked
through in CI (no display).

### Reliability

State is never held only in memory: spend requests, tasks, discovered cards and identity pins live in
SQLite WAL and are reconciled on every boot. Ambiguity resolves to inaction: an undeliverable approval
request is held, an unverifiable reply is not paid, a malformed recipient never reaches the wallet, a
transfer the wallet did not confirm is `TX_FAILED` with the reason stored. Upstream fragilities (the
module host dropping replies after its first event; the wallet aborting on a sequencer outage
mid-transfer) are documented in `KNOWN_LIMITATIONS.md` with the mitigations in place.

### Performance

Public-rail spends settle in the next block (~60 s on the public testnet) with no client-side proof.
Shielded transfers generate a real STARK: ~44 min wall on an 8 GB laptop, minutes on 16 GB. A cold wallet
replays the chain at ~1,000–3,000 blocks/min before it can answer. `agent.ask` runs inference
synchronously inside the delivery loop, so a long query serialises other inbound handling.

### Supportability

216 unit tests (`nix build .#unit-tests`), a Nim CLI test suite, and an end-to-end CI job that runs the
same `./demo.sh` a reviewer runs from a clean clone. `evidence/verify-testnet.sh` re-checks every recorded
transaction and account against the public chain. Module warnings go to the journal; every funding or
spend failure records its reason where `meta.status` and `wallet.history` can show it. Layout: one
implementation class split by concern (`pilot_identity`, `pilot_spending`, `pilot_owner`, `pilot_storage`,
`pilot_messaging`, `pilot_a2a`, `pilot_a2a_inbox`, `pilot_skill_registry`, `pilot_llm_*`) with a Nim CLI,
the owner-side library `owner_client.*` (one source for the `pilot-owner` console client and the
`pilot_owner` module) and two QML Basecamp plugins beside it.
