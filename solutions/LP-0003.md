# Solution: LP-0003 — Private Allowlist / Airdrop Distributor

**Submitted by:** edenbd1

## Summary

An airdrop where the eligibility set is committed on chain as a Merkle root and
never as addresses, and a recipient claims by proving membership on LEZ's
privacy-preserving path — so the chain records that *someone* eligible claimed,
and nothing about who. Double claims are stopped by a nullifier bound to the
recipient's secret, which an observer holding every candidate address still
cannot compute. Two distributions and 23 claims are live on the public testnet.

## Approach

**Which transaction path.** A LEZ *public* transaction does not verify a proof:
the sequencer re-executes the program host-side
(`lee/state_machine/src/program/mod.rs:73-77`, commented *"Execute the program
(without proving)"*). An airdrop built there would be a membership check wearing a
zero-knowledge costume. The path that works is the **privacy-preserving
transaction** — the client proves locally, LEZ's privacy circuit composes each
chained call with a real `env::verify`, and the sequencer checks the receipt
against the pinned circuit id. For that composition the callee must *be* a LEZ
program emitting a `ProgramOutput`, which is why `claim_lez` exists in that shape
rather than as a plain guest. It also has a consequence I depend on: a privacy
`Message` publishes neither `program_id` nor `instruction_data`, so the witness —
which carries the recipient's secret `nsk` — can travel in the instruction. On the
public path those bytes would be published verbatim, so a claim must never go
there. The tooling never does.

**Anchoring the root.** A membership proof establishes membership against whatever
root the statement names, which alone is worthless: anyone can build a one-leaf
tree holding themselves. So the root is anchored by address.
`create_distribution` initialises a PDA seeded by `[distribution_id, root]`, and
`claim` requires that PDA to be owned by the verifier. An invented root gives an
address nobody created, whose owner is the default — rejected (`4003`). No code
path trusts a caller-supplied root without that anchor.

**Secret-bound nullifiers.** Each claim occupies a PDA seeded by
`compute_claim_marker(distribution_id, nullifier)`, the nullifier being
`SHA256(CLAIM_NULLIFIER_PREFIX ‖ distribution_id ‖ nsk)`. The marker is `init`, so
a second claim targets an occupied PDA and is refused with
`AccountAlreadyInitialized` — shown against the deployed binary and live on chain.
Because the nullifier commits to `nsk`, an observer who knows every candidate
address still cannot compute it, so a marker maps back to nobody; because both it
and the marker seed commit to `distribution_id`, a claim cannot be replayed across
distributions.

**Delivery without a side channel.** The distributor publishes one `bundle.json`:
each recipient's claim data sealed to an X25519 key derived from their `nsk`
through a domain separator distinct from the nullifier and the account key,
authenticated with ChaCha20-Poly1305. A recipient trial-opens each row and keeps
the one whose payload reconstructs a leaf that anchors to the committed root — so
a malicious distributor cannot make them prove a leaf outside the set, and an
injected junk row is skipped rather than adopted. Non-contributory shared secrets
are rejected, so a crafted low-order ephemeral cannot collapse every recipient's
key to one value. `--pad` hides the count with rows that open for no one.

**No trusted setup.** Risc0 is a STARK: no ceremony, no reference string, no toxic
waste. `docs/privacy-model.md` states the assumptions in full.

## Live on the public testnet

A deploy hash is `SHA256(borsh(bytecode))` — content addressed — so the binaries
committed under `artifacts/programs/` hash to exactly these transactions, which
`scripts/verify-onchain-claim.sh` recomputes rather than trusts.

| | ImageID | Deploy tx |
|---|---|---|
| Claim program (LEZ-native) | `e9843420…67b57449` | `59c2160b…cbbea7c5` |
| Claim verifier (SPEL) | `31edc17c…a110385d` | `7b16e471…7092e34c` |

Two distributions are committed under that verifier with **23 claims** landed
against them (12 + 11). The full list of (distribution, claim tx, nullifier) is
committed at `artifacts/e2e/claims.tsv`, and each distribution is on chain in its
own right:

| | id | recipients | distribution PDA |
|---|---|---:|---|
| 1 | `b1…0001` | 12 | `6cPhtwbq…LawEHz` |
| 2 | `b2…0002` | 11 | `GfgURgai…e3q3TW` |

Both PDAs answer on chain today and both are owned by the verifier. Neither
address is asserted: a distribution's PDA is
`SHA256(prefix ‖ ImageID ‖ SHA256(id ‖ root))`, so deriving it from the id and the
root reproduces the address — which is what makes the root itself checkable rather
than a number to take on faith. The roots are
`e48c5f4fb3d964caa9974b3170810ec9834d708a17aab173f13a689ea6a45bcc`
and `7b5078e84ae56c70fac458165a8567572f9e0a00d5e339256f5bb109ed4eb44a`.
They are printed here rather than cited from a path because
`artifacts/e2e/dist*/` is gitignored — the distribution manifests are build
output, not tracked files — so these two numbers are the record.

A claim such as `441ccd15…ae112c86` renders on the block explorer as
`Privacy-Preserving Transaction` with its proof size. It names two public
accounts, the claim's marker and the distribution PDA, and **no recipient**: the
eligibility proof is verified without the claimant appearing on the page at all.
Which airdrop was claimed is public; who claimed it is not, and that is the
property a third party renders rather than one asserted here. Verify one from
public data:

```bash
CLAIM_TX=441ccd15e7b5eac388a0849481e95db409f1b6f23a202b6ee1a3ce37ae112c86 \
NULLIFIER=3db769e851c291d82cb79d717f1256710bb67b06a50cc52bea3f4ae1fea32b99 \
DISTRIBUTION_ID=b100000000000000000000000000000000000000000000000000000000000001 \
./scripts/verify-onchain-claim.sh
```

It confirms the transaction is `PrivacyPreserving`, its receipt a `Succinct` STARK
the sequencer verified, and the marker PDA owned by the verifier: the membership
proof was verified on chain as a precondition of acceptance. Of those three values
only `CLAIM_TX` is a transaction — the nullifier seeds an address and the
distribution id is an identifier, so `getTransaction` returns `null` on both.
Expected, not a dead link.

> Built against **LEZ v0.2.4** (`47eba25`), which is why these ImageIDs differ from
> any earlier v0.2.0 or v0.2.2 write-up, and the deploy transactions with them: a
> new ImageID is a new deploy. The ImageID moves even where dependency sources do
> not, because a guest's panic messages embed the cargo checkout path and that path
> carries the pinned revision. SPEL has no release targeting a current LEZ, so
> `vendor/spel` carries the upstream v0.6.0 sources repinned and ported.

## Success Criteria Checklist

### Functionality

- [x] **A distributor can commit to an eligibility set on-chain without revealing individual addresses.**
 Only the Merkle root, in a PDA seeded by `[distribution_id, root]`; the set may also be published encrypted (`crates/airdrop-crypto`).

- [x] **An eligible recipient can claim their allocation without revealing which address in the set they hold.**
 A membership proof on the privacy path; the witness never reaches the journal and a privacy tx publishes no instruction data.

- [x] **A recipient cannot claim more than once (double-claim prevention via nullifiers or equivalent).**
 Marker PDA under `init`; tested against the deployed binary and live on chain.

- [x] **An on-chain observer cannot link a completed claim to any specific address in the eligibility set.**
 Secret-bound nullifier; `docs/privacy-model.md`.

- [x] **The submission documents its full privacy model: what on-chain observers learn, what the distributor learns, at which points in the claim flow identity information is revealed or withheld, and where trade-offs or residual leakage remain. Claims of privacy must be precise — "unlinkable" must be defined relative to a stated threat model.**
 Threat model and named residual leakage: `docs/privacy-model.md`, `docs/limitations.md`.

- [x] **A reference integration is delivered: a working demo of a private airdrop or allowlist gate on LEZ testnet.**
 `scripts/deploy-and-claim.sh` runs the full create-then-claim flow; its result is the live claims in `artifacts/e2e/claims.tsv`.

- [x] **At least 2 distinct distributions are deployed on LEZ testnet, with a combined total of at least 20 unique claims completed across them; the distributions must be reproducible and evidence must be provided.**

### Reliability

- [x] **The system handles proof generation failures gracefully and surfaces a clear error to the claimant.**
 `claim-from-bundle` verifies the witness locally before emitting anything, so a bad witness fails in microseconds rather than after proving.

- [x] **A failed or rejected claim does not mark the claimant as having claimed, allowing a retry.**
 The marker is written only on success.

- [x] **The verifier program returns deterministic, documented error codes for all invalid-proof and double-claim scenarios.**
 Five of them, `4001`–`4006` with `4005` reserved, in `docs/error-codes.md` — each row naming the attack it stops, what the claimant should do, and the test that watches it fire against the deployed binary. `4001` was the last without one: it fires on the witness decode, before any binding, so no mutation of a well-formed claim reaches it and the test supplies the undecodable words itself.

## FURPS Self-Assessment

### Functionality

Two instructions. Four documented bindings — anchored root, secret-bound
nullifier, one marker per claim, destination — each with adversarial coverage.
**Limitations, stated rather than buried:** the destination is bound inside the
proof but is not published and not folded into the marker seed, so it serves a
delivery step in the same transaction, not a standalone on-chain record; the
encrypted bundle reveals the recipient count unless padded, and padding hides it
from a counter but not from an observer measuring row length;
`create_distribution` is permissionless, so an integrator should key
proof-of-claim on `(distribution_id, root)`, not `distribution_id` alone.

### Usability

Two surfaces over one library — the `airdrop` CLI and the Basecamp app —
computing the same commitments from the same code. Onboarding is
`git clone && ./scripts/demo.sh`. The CLI's refusals are written to be read by a
human and explain why. The `.lgx` ships `darwin-arm64` and `linux-amd64`; the CLI
is the cross-platform path beyond those.

### Reliability

Local pre-verification before proving; a marker written only on success;
deterministic error codes. The scripts confirm a claim by polling `getTransaction`
over RPC rather than by trusting the block explorer, which lags the sequencer by
about an hour and three quarters on this chain — so a landed claim is never
mistaken for a failed one. I filed that lag as
[`lez-explorer-ui#15`](https://github.com/logos-blockchain/lez-explorer-ui/issues/15)
and **closed it myself as not a bug**: re-measured, the explorer does index
privacy transactions and I had checked too soon. The retraction is in the issue.

### Performance

`claim` at 1.56 % of the public compute budget, in a single segment. Wall-clock is
dominated by proving and runs to minutes rather than seconds at
`RISC0_DEV_MODE=0`. It is deliberately not quoted as one fixed number: the same claim
measurably slows when an unrelated build competes for the cores.
`scripts/prove-one-claim.sh` times it and prints what it measured, and the demo
shows that clock running rather than asserting a figure. That latency, not the
cycle count, is the real constraint on a lifecycle run.

### Supportability

31 tests across the workspace, nine of which drive the deployed binary through
the sequencer's own executor, all green in CI, which runs the adversarial e2e unconditionally and fails
on any ImageID drift. The two guest crates sit outside the host workspace because
they target `riscv32im-risc0-zkvm-elf`, but the deployed verifier is still under
test: `claim-verifier-tests` exercises the built binary, including the anchoring
check, with a case a weaker form of it would let through.
