# Solution: LP-0002: Private M-of-N Multisig: LEZ-Quorum

**Submitted by:** FidelCoder

## Summary

Quorum is a private M-of-N treasury for LEZ v0.2.2. It lets members authorize
public transfers and governance changes without placing member account IDs or
approval ownership in public state. A Risc0 threshold receipt proves private
credential membership and emits proposal-scoped nullifiers; the outer LEZ
privacy proof authorizes those credential accounts; and a SPEL gate binds both
proofs, accumulates distinct approvals, and executes at threshold.

This is a follow-up to [PR #123](https://github.com/logos-co/lambda-prize/pull/123),
with published Basecamp assets, refreshed technical documentation, verified
completion evidence, and the final Basecamp and CLI recordings.

## Approach

The constitution stores a deterministic Merkle root over commitments to LEZ
regular-private-account IDs. A member proves private account derivation and a
Merkle path in the threshold guest. The guest derives:

```text
nullifier = SHA256(
  "quorum/v1/nullifier" || member_secret
  || proposal_id_le64 || constitution_version_le32
)
```

That scoping makes a repeated approval public and rejectable without creating
a stable identifier across proposals. A second scoped commitment binds each
threshold witness to the same private credential account authorized by the
outer LEZ proof.

This avoids the public multisig approach of claiming fresh, zero-nonce member
accounts. Quorum never changes a private member account's `program_owner` or
assumes its nonce is zero; LEZ's privacy protocol remains the owner and proves
the normal private account transition. Public gate state contains only the
member-set shape, policy, proposals, approval nullifiers, and results.

Per-member receipts make partial approvals independently submit-able and
restart-safe. The SDK also supports an aggregated M-member receipt. Risc0
succinct STARK receipts were selected so the gate can verify a pinned guest
statement through proof composition. The current path does not request the
Groth16 wrapper and has no Quorum-specific trusted setup.

LEZ is essential here because its private account proof authorizes the member
credential while SPEL provides deterministic public gating and token chained
calls. A centralized coordinator could conceal a member list operationally,
but users would have to trust it to count votes, prevent replays, and execute
the approved action correctly.

## Success Criteria Checklist

### Functionality

- [x] Any M-of-N shielded member can approve without public identity: the
  witness contains the member credential and Merkle path; the journal contains
  neither.
- [x] The gate confirms threshold without recording member identities: proposal
  state stores only scoped nullifiers and their count.
- [x] Double voting is prevented in-circuit and across transactions by a
  proposal- and constitution-version-scoped nullifier.
- [x] Execution is not linked to an individual private account by protocol
  outputs. Public timing and network metadata limitations are documented.
- [x] Proof generation runs client-side. A real 2-of-3 proof completed in
  `675.542 s` and produced a `224,866` byte succinct receipt in CI.
- [x] A threshold-gated transfer runs on LEZ testnet using private member
  credentials.
- [x] One 2-of-3 instance was initialized, proposed, privately approved twice,
  and executed at blocks `9021` through `9544`; exact evidence is linked below.
- [x] The public repository includes the circuit, gate, SDK, CLI, Basecamp
  module, tests, scripts, and complete required write-up.

### Usability

- [x] `quorum-sdk`, `quorum-composer`, and `quorum-cli` provide library and
  operator integration surfaces.
- [x] Native and portable Basecamp LGX 0.1.1 packages, the matching CLI, and

## Performance

LEZ v0.2.2 guest execution used one warmup and three measured runs:

| Operation | User cycles |
|---|---:|
| Initialize constitution | 75,173 |
| Create token | 97,284 |
| Initialize recipient | 104,491 |
| Initialize vault | 322,246 |
| Fund vault | 128,649 |
| Propose transfer | 154,336 |
| Approve one member | 300,267 |
| Execute transfer | 499,819 |
| Propose / execute rotation | 150,486 / 307,506 |
| Propose / execute threshold change | 132,404 / 292,096 |

One reported CU here is one guest user cycle returned by Risc0
`SessionInfo::cycles()`, excluding continuation and power-of-two padding
overhead. The pinned LEZ execution code uses a fixed cycle limit and identifies
fees as future work; its RPC exposes no per-transaction gas-used or fee-paid
result. No numeric cryptographic verification gas charge is claimed, and the
approval guest row must not be read as the cost of verifying the final privacy
receipt.

Full methodology, real-proof timings, and pinned upstream sources:
<https://github.com/lezQuorm/LEZ-Quorum/blob/main/docs/BENCHMARKS.md>

## FURPS Self-Assessment

### Functionality

Quorum implements private authorization for transfers, member rotation, and
threshold changes. Proposal contents and approval counts are intentionally
public; cancellation and expiry are not implemented.

### Usability

The Rust SDK, crash-safe CLI, SPEL IDL, and Basecamp module expose the same
lifecycle. Public writes require preview and explicit confirmation. Existing
arbitrary wallet credential discovery is not yet a complete UI workflow.

### Reliability

Consensus checks fail closed with stable errors. On-chain nullifiers preserve
partial approvals, and the client journal prevents blind retries after unknown
submission results.

### Performance

The real client proof is minutes rather than interactive seconds, and the full
recursive LEZ flow can take hours without acceleration. Guest compute and
client proof time are measured separately.

### Supportability

Compatibility-sensitive inputs are pinned. Tests cover cryptographic
derivations, circuit failures, gate state, IDL consistency, SDK/CLI flows,
transaction reconciliation, Basecamp packaging, a standalone sequencer, and a
real threshold proof. The project remains unaudited and retains upstream
advisories in pinned dependencies.
