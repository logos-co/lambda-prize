# Solution: LP-0002 — Private M-of-N Multisig for LEZ

**Submitted by:** duongja

## Summary

This submission implements a private M-of-N multisig for LEZ where approvals are
collected privately, the chain verifies threshold satisfaction without exposing
which members approved, and duplicate approvals are prevented with
proposal-scoped nullifiers.

The repository includes:

- the LEZ verifier program and guest execution path,
- client-side proof preparation and aggregation tooling,
- a reusable Rust SDK surface,
- a Basecamp GUI that drives the real localnet and hosted testnet execution
  path,
- reproducible local and hosted evidence scripts,
- narrated demo video and reviewer-facing evidence documents.

## Approach

### Privacy Model

Each multisig member is represented by a private membership secret and a leaf in
a deterministic Merkle membership root. Member approvals are converted into
proposal-scoped approval artifacts, then aggregated into a threshold approval
payload.

The chain learns:

- the public multisig configuration,
- the public proposal,
- the threshold count,
- the final approval count,
- the executed aggregate hash.

The chain does not learn which specific members approved the proposal.

### Double-Approval Prevention

Each approval carries a proposal-scoped nullifier. Aggregation and verification
reject duplicate nullifiers, which prevents the same member from approving the
same proposal twice.

### On-Chain Program Shape

The LEZ v0.2 program exposes three core instructions:

- `create_multisig`
- `propose`
- `execute_private`

The runtime handler path executes on `lee_core`. The published IDL is generated
from a thin SPEL wrapper source and is validated in repository preflight.

### Client and GUI Integration

The repository includes:

- a Rust SDK surface in `private_multisig_core::sdk`,
- CLI commands for member generation, config creation, proposal creation,
  approval, aggregation, verification, and proving,
- a Basecamp QML + C++ app that calls the real Rust backend and drives the real
  hosted testnet execution path.

The Basecamp threshold controls are not cosmetic. They shape the actual config,
aggregate, and on-chain execution.

## Success Criteria Checklist

### Functionality

- [x] Any M-of-N member holding a shielded LEZ account can submit an approval
      without revealing identity on-chain.
- [x] The on-chain verifier confirms a threshold of approvals without recording
      which members approved.
- [x] A member cannot approve the same proposal twice.
- [x] Completed execution is unlinkable to any individual member's shielded
      account at the on-chain approval level.
- [x] Proof generation runs client-side on a standard laptop.
