# Solution: LP-0002 - LEZ-Quorum Private Threshold Treasury

**Submitted by:** FidelCoder

## Summary

LEZ-Quorum is a private threshold treasury for Logos Execution Zone (LEZ).
An M-of-N group can authorize transfers, membership rotations, and threshold
changes without publishing its member list or attributing approvals to named
members.

The implementation now targets the live LEZ v0.2.2 protocol. It includes the
credential-aware RISC Zero circuit, SPEL gate, private transaction composer,
Rust SDK and guarded network CLI, generated IDL, and Basecamp module. Both
development-mode and real-proof local lifecycles have passed end to end. The
public 2-of-3 lifecycle also completed with two real private approvals and
execution confirmed at block 1165.

## Approach

The constitution stores one Merkle root over commitments to LEZ regular
private-account credentials. Each approval proves control of the credential's
nullifier secret and ML-KEM viewing public key, membership under the active
root, and a distinct proposal- and constitution-bound nullifier. The proof
also binds the proposal, policy, outer LEZ private account, recipient, vault,
transfer tier, and amount cap.

The gate verifies the threshold receipt as a RISC Zero assumption, checks LEZ
positional account semantics, updates the proposal, and preserves the privacy
boundary. The composer verifies the stored threshold artifact against the
pinned image, attaches it while proving the gate, passes the gate receipt into
the LEZ privacy circuit, and produces a signed `PrivacyPreservingTransaction`.
The network workflow journals exact transactions before submission, requires
explicit public-write approval, polls by hash, and reconciles ambiguous
timeouts before any exact resubmission.

Membership rotation is threshold-authorized and atomic. Tests reject early
activation and retired credentials while demonstrating replacement activation.
The generated IDL covers all instructions, state accounts, custom types, and
errors 4001-4017, with client, FFI, and codec round-trip coverage.

The Basecamp module contains QML views, Qt Remote Objects definitions, CMake,
pinned Nix packaging, and a hardened native QProcess backend. The backend uses
an operation allowlist, invokes no shell, forces non-development proving,
protects its working directory, streams output, supports cancellation, and
enforces operation-specific timeouts. Its Local and LEZ Testnet modes expose
live approval progress, guarded execution, and transaction reconciliation.

threshold changes, and atomic membership rotation for an M-of-N treasury. Its
public 2-of-3 lifecycle is confirmed through execution and final state reads.

The repository provides a Rust SDK, guarded local/testnet CLI, generated IDL,
and Basecamp module. Network writes are journaled before submission and require
an explicit approval flag. Native and portable Basecamp packages build from
pinned inputs.

### Reliability

Typed failures and rejection tests cover invalid credentials, duplicate votes,
tampered or missing receipts, stale proposals, account-ordering errors, and
unsafe transaction retry behavior. Both development-mode and real-proof local
lifecycles completed successfully.

real nested proof lifecycle took about 2 hours 19 minutes on a 15 GiB machine
with 21 GiB total swap. Each public approval proof took about 1 hour 23 minutes
on the same 15 GiB host with 16 GiB total swap.

### Supportability

The implementation is pinned to exact LEZ and SPEL revisions and is covered by
101 Quorum tests, 302 SPEL workspace and fixture tests, strict Clippy, local
LEZ lifecycle tests, reproducible Nix packaging, and operational documentation.
Production use still requires an independent security audit.

## Privacy Boundary

Private inputs include LEZ nullifier secret keys, ML-KEM viewing secret keys,
private credential account IDs, the enrolled member list, Merkle positions and
paths, and private post-state contents. Proof artifacts expose
proposal-scoped bindings rather than stable member pseudonyms.

Public state includes multisig and proposal IDs, policy, member root and count,
proposal action and status, approval count, Quorum nullifiers, and governance
changes. Public program deployment does not establish network-level sender
anonymity or replace an independent audit.

## Reproduction

```bash
git clone --branch v0.2.2 --depth 1 \\
  https://github.com/logos-blockchain/logos-execution-zone.git
git clone https://github.com/FidelCoder/LEZ-Quorum.git

cd LEZ-Quorum
cargo fmt --all -- --check
RISC0_DEV_MODE=1 CARGO_BUILD_JOBS=2 \\
  cargo clippy --workspace --all-targets --all-features -- -D warnings
RISC0_DEV_MODE=1 CARGO_BUILD_JOBS=2 \\
  cargo test --workspace --all-targets --all-features -- --test-threads=1
RISC0_DEV_MODE=1 ./scripts/demo.sh

# Terminal A: local LEZ v0.2.2 sequencer
cd ../logos-execution-zone
RISC0_DEV_MODE=1 just run-sequencer-standalone

# Terminal B: choose a fresh identity seed for persistent chain state
cd ../LEZ-Quorum
RISC0_DEV_MODE=1 CARGO_BUILD_JOBS=2 \\
  cargo run -p quorum-composer --features network \\
  --example local_lez_e2e -- http://127.0.0.1:3040 111

# Guarded testnet preflight and transaction preparation
cargo build --release -p quorum-cli
env -u RISC0_DEV_MODE target/release/quorum network --target testnet health
env -u RISC0_DEV_MODE target/release/quorum network --target testnet deployment
env -u RISC0_DEV_MODE target/release/quorum network --target testnet status
env -u RISC0_DEV_MODE target/release/quorum network --target testnet reconcile

cd apps/basecamp-quorum
nix build .#generate .#lib .#lgx .#lgx-portable
```

Exact transaction handling and the current testnet state are maintained in the
deployment and readiness documents.
