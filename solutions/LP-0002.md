# Solution: LP-0002 - LEZ-Quorum Private Threshold Treasury

**Submitted by:** FidelCoder

## Summary

LEZ-Quorum is a private threshold treasury for the Logos Execution Zone. An
M-of-N group can authorize transfers, membership rotations, and threshold
changes without publishing the member commitment list or attributing proof
nullifiers to individual members.

This is an active research implementation. It provides a tested local
threshold circuit, prover, state machine, SDK, CLI, and SPEL gate, but it does
not yet satisfy every LP-0002 deployment criterion. The remaining boundaries
are stated explicitly below.

## Approach

The constitution stores one Merkle root over member commitments. A Risc0 proof
shows that distinct member secrets belong to that root, derives
proposal-and-version-bound nullifiers, meets the requested threshold, and
approves a policy-valid action. The gate binds proposals to a multisig account
and constitution version, rejects duplicate nullifiers, re-derives transfer
tier policy, validates the recipient and treasury vault PDA, and applies the
approved transition.

Membership rotation is threshold-authorized and atomic. The CLI preserves a
private replacement bundle, refuses early activation, validates the bundle
against the active constitution, removes surplus retired local key files, and
demonstrates successful approval by replacement members.

The hardened gate now includes:

- multisig, proposal ID, constitution version, recipient, vault, and tier-policy
  bindings;
- member and tier bounds, checked counters, malformed-claim checks, and atomic
  failed-state handling;
- removal of the unauthenticated reject instruction; and
- an approve instruction that carries only the public journal, with the Risc0
  receipt expected as an outer-executor assumption.

The current circuit proves knowledge of a Quorum-specific member secret. The
lez-compat crate models LEZ v0.3 shielded account commitments and validation
rules, but it is not yet wired into the membership witness. The implementation
therefore does not yet prove control of a live shielded LEZ account.

The SPEL guest calls Risc0 env::verify, so a LEZ transaction composer must
attach the threshold receipt as an assumption to the outer executor. That
composer, the network client, and standalone-sequencer tests are still
pending. Local gate tests verify state rules but are not presented as
end-to-end on-chain receipt verification.

The generated IDL contains the four instruction layouts but currently lacks
definitions for externally declared custom argument and account types. A
complete client-consumable schema remains pending.

## FURPS Self-Assessment

### Functionality

The local implementation covers constitution creation, tiered transfers,
individual and aggregated approvals, threshold execution, member rotation,
threshold changes, and replacement-key activation. Live shielded-account and
network execution boundaries remain open and are not counted as complete.

### Usability

The CLI and SDK provide a reproducible local workflow with typed errors and
mode-0600 operational files. The Basecamp QML is a prototype until its native
backend and package are implemented.

### Reliability

Proposal ownership, version, recipient, tier, vault, and instruction-ID
bindings are enforced. Counters are checked, malformed claims are rejected,
failed mutations are atomic, old keys fail after rotation, and replacement
keys are exercised. Network retries and reconciliation remain untested.

### Performance

A real RISC0_DEV_MODE=0 aggregated 2-of-3 proof completed in 417.435 seconds.
The serialized receipt was 224,346 bytes and re-verified successfully on the
host. Network verification cost and transaction compute usage are unknown.

### Supportability

The workspace separates domain, compatibility, circuit, prover, gate, SDK,
CLI, and UI concerns. The public README and technical documents describe the
implemented boundary, security assumptions, known limitations, and prioritized
integration work. The code has not been independently audited.

## Privacy and Security

**Private in the proof:** member secrets, commitment list, Merkle leaf
positions, and Merkle authentication paths.

**Public by design:** multisig ID, constitution version, threshold, member
count, member root, tiers, proposal action and status, approval count, and
nullifiers.

A rotation is observable because its action, root, member count, and
constitution version change. The implementation claims that identities and
old-to-new member mappings are hidden by the commitment scheme; it does not
claim rotations are invisible.

Transaction sender unlinkability has not been demonstrated because the live
LEZ transaction path is pending. The implementation has not received an
independent security audit.
