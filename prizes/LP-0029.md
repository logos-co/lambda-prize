# LP-0029: Private Messaging App [DRAFT]

**`Status: Draft`**
**`Logos Circle: N/A`**

## Overview

This prize is for a private messenger for Logos Basecamp that people can use as their everyday chat app: 1:1 and group conversations, contacts, file sharing, and local history, with no account tied to a phone number or email address and no server that sees who talks to whom.

The cryptography and conversation protocols already exist in the Logos Chat module (`chat_module`, wrapping [libchat](https://github.com/logos-messaging/logos-chat)). This prize funds the application on top of it: the contact, verification, attachment, local-storage and privacy work that turns a working protocol into a messenger.

## Motivation

The widely used private messengers encrypt message content, but registration is tied to a phone number and every message passes through servers run by one operator. That operator learns who is online and when, can be compelled to hand over what it holds, and is a single point that states can block: Iran blocked Signal in 2021 and Russia in 2024.

Logos Chat removes the central operator. Messages travel over Logos Delivery, a peer-to-peer network, and are end-to-end encrypted, with de-MLS for group conversations. Addresses are public keys, not phone numbers.

What exists today is a protocol and a demonstration UI ([`logos-chat-ui`](https://github.com/logos-co/logos-chat-ui)). It shows two instances exchanging messages, but it is not something a journalist and a source, or a Logos Circle, would rely on: contacts are pasted hex addresses with no way to check who is on the other end, there is no file sharing, and nothing protects the local history on a shared or seized machine. These are application-layer problems with several reasonable designs, which suits a competitive prize better than an RFP.

### Starting point

As of `chat_module` v0.3.0:

- Each launch creates a new installation with a new address; earlier conversations become read-only history. Persisting the installation has landed in libchat and is expected in a later module release. This prize does not open until that release ships.
- Group conversations are limited to 20 participants ([logos-chat#199](https://github.com/logos-messaging/logos-chat/issues/199)).
- Delivery receipts are not emitted ([logos-chat#121](https://github.com/logos-messaging/logos-chat/issues/121)).
- Key packages and account device lists are fetched from a registry over HTTP, which is planned to move to a LEZ-based service.
- Content is plain text. libchat defines text and reply content types.

## Success Criteria

### Functionality

**Identity and contacts**

- [ ] The user's identity and conversations persist across app restarts, and conversations continue after a restart without re-inviting anyone.
- [ ] A user can share their contact as a copyable string and as a QR code. Adding a contact from either opens a conversation with them without manual address handling.
- [ ] Contacts can be given local names. Names are never sent to the network.
- [ ] **Contact verification**: two users can confirm out of band that they hold each other's real keys, by comparing a short code or scanning a QR code. The app shows which contacts are verified and warns when a verified contact's keys change.

**Conversations**

- [ ] 1:1 and group conversations: create a group, invite members, show the roster with pending invites, and leave or remove members where the chat module supports it.
- [ ] Replies to a specific earlier message.
- [ ] Each sent message shows its state (pending, sent, failed). A failed message can be retried, and unsent messages survive an app restart.
- [ ] Unread counts per conversation, and local search over message history.
- [ ] Desktop notifications for new messages. By default they show neither message content nor sender name.

**Attachments**

- [ ] A user can send images and files of at least 10 MB in 1:1 and group conversations. The file is encrypted on the sender's device with a key generated for that file, uploaded to **Logos Storage**, and the reference, key and hash are sent inside the end-to-end encrypted message. The recipient downloads, checks the hash, and decrypts. Storage nodes only ever hold ciphertext.
- [ ] Images display inline after download. Other files can be saved to disk.

**Local data**

- [ ] The local database (chat state and message history) is encrypted at rest. The key comes from a user passphrase through a memory-hard KDF or from the OS keychain.
- [ ] The app can be locked and unlocked with the passphrase.
- [ ] A user can delete a single conversation, and can wipe all local data for the app in one action.

**Privacy**

- [ ] The app makes no network requests outside the Logos stack: no link previews, no remote avatars, fonts or images, no update checks, no telemetry. Infrastructure that the chat module itself uses, such as its key registry, counts as part of the Logos stack.
- [ ] A **privacy statement** of no more than two pages describes what each party can learn: a passive network observer, Logos Delivery peers and store nodes, the key registry, Logos Storage nodes, and the other members of a conversation. It separates what is inherited from the chat module and Delivery from what the app adds, and states what the app does not protect against.

### Usability

- [ ] A Logos Basecamp app with local build instructions, loadable in Basecamp and installable from a module catalog.
- [ ] Usable by a non-expert: adding a contact, verifying them, starting a group and sending a file work without reading documentation, and pending, offline and error states are clear. This is judged on overall impression: evaluators will use the app as an ordinary user would.
- [ ] Application logic beyond the UI (contacts, verification, attachments) lives in a Logos module with a documented API, so other Logos apps can reuse it without this app's UI.

### Reliability

- [ ] Messages sent while the recipient is offline are received after they reconnect, within the retention the chat module and Logos Delivery provide. The README documents that retention.
- [ ] Sends made while offline are queued and sent on reconnect, and the app shows its connection state.
- [ ] Attachment uploads and downloads retry on transient failure and report a clear error after giving up. An incomplete or hash-mismatched download is never displayed or saved.
- [ ] Invalid contact strings, oversized files and unknown conversations produce a clear error, not a crash.

### Performance

- [ ] Message latency between two instances on testnet 0.4 is measured over at least 100 messages and the median and 95th percentile are reported.
- [ ] A conversation with 5000 messages in local history opens and scrolls without noticeable delay. Report the time to open it.
- [ ] The app does not poll the network beyond what the chat module does.

### Supportability

- [ ] Deployed and operating end-to-end against Logos testnet 0.4.
- Platform support (recommended): all platforms Logos Basecamp supports, i.e. **Linux** and **macOS**, and from testnet 0.4 also **Windows** and **Android**. macOS coverage is checked through the Adoption criteria.
- [ ] Logos Basecamp modules are built with [`logos-module-builder`](https://github.com/logos-co/logos-module-builder).
- [ ] Logos Basecamp modules are published to a module catalog: a fork of [`logos-modules-release-base`](https://github.com/logos-co/logos-modules-release-base), publishing releases via [`logos-modules-release-action`](https://github.com/logos-co/logos-modules-release-action).
- [ ] Integration tests run at least two instances against each other and cover a 1:1 exchange, a group exchange, an attachment round trip and a restart. They are included in CI, and CI is green on the default branch.
- [ ] A README covers building, installing from the catalog, and each user flow above.

## Adoption

> These metrics measure traction attributable to a given submission for this prize.
>
> **All of the following are required in addition to the success criteria above**, except where marked *(Discretionary)*. We publish the dimensions we look at, but hitting a raw number is not by itself sufficient (see [Terms & Conditions](../TERMS.md) for the evaluation policy that applies to all prizes). Volume that is clearly manufactured does not count, regardless of the headline number.
>
> Private chat leaves no public trace and the app must not collect analytics, so adoption is shown through communities that use it and agree to have that use checked, not through usage counts.

- [ ] **Community use.** At least 3 communities independent of each other and of the submitting team, at least one of them a Logos Circle, use the app as a regular channel for their own coordination for at least 2 months. For each: a named steward, a written statement of what the group uses it for and since when, and a re-confirmation at the end of the window. A community that has stopped using it does not count.
- [ ] **Verification by evaluators.** For each of those communities, the steward invites an evaluator into a group conversation the community uses, with its members' knowledge. Over the following 2 weeks the evaluator sees messages from at least 5 distinct members. Across the 3 communities, at least 30 distinct members are seen.
- [ ] **macOS.** Members on both Linux and macOS are present in at least one of those groups, confirmed by the steward.
- [ ] **Bug reports.** At least 10 reproducible issues were opened by people outside the submitting team and resolved with a linked fix. Median first response is under 7 days over the observation window.

**Discretionary**

- Testimonials from people who used the app, each describing what they used it for. Evaluators will contact a random sample and ask what they did with it; unanswered or generic replies count against the submission. Account tenure and posting history are inspected.
- Another Logos app or λPrize submission reuses the app's module (for example contacts, verification or attachments) as a dependency.
- An independent review, by someone outside the submitting team, of the app's local-data protection or its privacy statement, with any findings fixed.
- Tutorials or walkthroughs by people outside the submitting team, or use in a Logos-run workshop or Circle meetup.

**Not counted.** Stars, forks without divergent commits, follower counts, impressions, likes and reposts, waitlist or newsletter signups, package download counts, and site visits are not adoption evidence and are not counted in any position, required or discretionary.

## Additional Design Choices Left to the Submitter

The following are deliberately not set out in the Success Criteria, as they are additional design choices which the submitter should decide upon. A submission must pick a position on each, document it, and justify it: the reasoning is part of what is evaluated.

- **Contact format and verification code.** What a contact string contains, how the verification code is derived from the two parties' keys, and how a key change is detected and presented.
- **Local key management.** Passphrase, OS keychain, or both; what happens when a passphrase is forgotten; whether the app locks itself after inactivity.
- **Attachment availability.** Who keeps an uploaded file available on Logos Storage and for how long, and what a recipient sees when it is gone.
- **Mix routing.** Whether to send through the Logos mixnet if it is available to Basecamp apps on testnet 0.4, and the latency cost of doing so.
- **Disappearing messages.** Whether to offer them, and how the app is honest about the fact that a recipient's device cannot be forced to delete anything.

## Scope

### In Scope

- The messenger Basecamp app and its reusable module.
- Contacts, contact verification, attachments over Logos Storage, local encryption and wipe.
- The privacy statement.
- Integration tests, CI and catalog publication.

### Out of Scope

- Changes to the chat protocol, its cryptography, or `chat_module`. Problems found there should be reported upstream.
- Voice and video calls.
- Linking several devices to one account, unless the chat module supports it by the time of submission.
- User discovery by phone number, email or any directory.
- Bridges to other messengers.
- Large public channels and broadcast feeds. Public discussion is covered by [LP-0026](LP-0026.md).
- Use of LEZ or the blockchain module.

## Submission Requirements

- Public repository (MIT and Apache-2.0) with the app, its module, tests and README.
- The module catalog's `logos-repo.json` URL, so evaluators can install the app through the package-manager UI or `lgpd`.
- The privacy statement.
- The latency and history performance results.
- Evidence for each adoption criterion: steward statements and contacts, and links to the resolved issues.
- A narrated video walkthrough (see [demo requirements](../README.md#evaluation-policies)) showing two users adding and verifying each other, a 1:1 and a group conversation, a file sent and received, a restart with conversations intact, offline send and recovery, and the lock and wipe flows. The builder should explain the main design choices listed above.
- A FURPS self-assessment as part of the solution (see [solution template](../solutions/LP-0000.md)).
- GitHub issues filed for any problems encountered with Logos technology.

## Evaluation Process

Submissions are evaluated first-come-first-served against the success criteria. The first submission that meets all criteria wins.

This prize opens once a `chat_module` release keeps an installation's identity across restarts and is usable on testnet 0.4. Because the adoption criteria require at least 2 months of community use, builders are encouraged to release early and start gathering users while they continue to develop.

Evaluators will install the app from the submitted catalog on a clean machine and use it as described in the README. Evaluators may also ask technical follow-up questions to verify authorship and understanding of the implementation.

The following policies apply to all prizes (see [evaluation policies](../README.md#evaluation-policies)):

- **Submissions:** each builder (or team) is allowed a maximum of **3 submissions** per prize, with at most **one submission/review per week**.
- **Feedback:** initial evaluation feedback is limited to a pass/fail indication against the success criteria.
